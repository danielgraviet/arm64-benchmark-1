## Update: `RLP_MIGRATABLE=0` does not help; the crash looks like a template-snapshot timing problem

**Setup.** Same cell as above (stock Firecracker v1.16.1, guest `6.12.34-rlp1`, host `6.17.0-1032-nvidia-64k`), `RLP_BURST_MAX_CPU=2`. Every arm resumes **the same on-disk template** (`template=hit` on every clone, including the first one after each runner restart). Arms were interleaved M1 → M0 → M1b. Each arm ran 3 warmups of 10 plus 5 batches of 100 creates, kept alive (`--keep`), with guest serial logs scanned for an oops before cleanup.

| arm | `RLP_MIGRATABLE` (`enable_diff_snapshots` on load) | oops / clones (batches) | per batch |
|---|---|---|---|
| M1 | 1 | 46 / 497 (9.3%) | 10, 12, 10, 6, 8 |
| M0 | 0 | 33 / 496 (6.7%) | 0, 4, 4, 12, 13 |
| M1b | 1 | 23 / 498 (4.6%) | 2, 5, 6, 2, 8 |

Pooled, dirty tracking on is 69/995 (6.9%) vs off 33/496 (6.7%). **No effect**; the batch-to-batch spread is larger than the arm difference. Every probe failure was an oopsed guest: `missing` (sandbox never answered `echo ready`) equals `oops` in each batch to within 1–2, and the 4 explicit `failed` records are `bad gateway` from the toolbox proxy.

**Signature, identical in all arms** (one trace saved per batch):

```
[    1.154424] Internal error: Oops: 0000000096000046 [#1] PREEMPT SMP
[    1.154672] CPU: 1 UID: 0 PID: 179 Comm: tokio-rt-worker Not tainted 6.12.34 #2
pc : __rb_erase_color+0x16c/0x284
lr : vma_interval_tree_remove+0x1b4/0x2fc
Call trace:
 __rb_erase_color / vma_interval_tree_remove / unlink_file_vma_batch_final / free_pgtables /
 exit_mmap / __mmput / mmput / do_exit / do_group_exit / ... / do_signal / do_notify_resume / el0_ia
```

(One trace out of 9 had `pc : set_root` instead.)

**What this points at**

- Guest uptime at the oops is **1.154 s every time**, which is the template's snapshot instant. The faulting task is in `do_exit` → `exit_mmap` **on vCPU 1**.
- `Comm: tokio-rt-worker` is the daemon's thread name, which a forked child keeps until it calls `exec`. The template build pauses **right after** `WarmToolboxInNetns` drives warmup execs (`runner/internal/vm/template.go:1047-1055`, then straight to the pause). So the most likely story is that the snapshot captures a warmup child still tearing down its mm on vCPU 1, and finishing that teardown after resume corrupts the VMA interval tree in some fraction of clones.
- It is racy, not deterministic: every clone resumes byte-identical state, yet only ~5–10% oops. That fits a vCPU 0 / vCPU 1 interaction after resume, or restore-time state on the second vCPU (TLB, cache or VMID handling with 64 KiB host pages), more than a corrupt image.
- 1-vCPU clones of a template built the same way hang ~1e-4 (earlier comment). Plausibly the same in-flight-exit window with no second vCPU to race against.

**Suggested next experiments** (cheap, runner-only):

1. **Quiesce before pausing:** after the warmup, wait until the daemon has reaped its warmup children (or sleep 100–500 ms), then pause. If the rate drops to ~0, the fix is a settle step in the template build, and that is worth having regardless.
2. **Per-template variance:** rebuild the template N times and measure the oops rate per template. A bimodal result (some templates 0%, some high) confirms snapshot-timing dependence.
3. If 1 doesn't fix it: the same test on the 4 KiB host kernel (`6.17.0-1032-nvidia`, installed on HQ Vera) to separate the 64 KiB-page restore path.
