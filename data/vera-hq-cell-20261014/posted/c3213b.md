## 1-vCPU clones oops too, and the traces point at the same snapshot-timing window

Earlier I reported that 1-vCPU clones *hang* about 1e-4 of the time with no oops. With more sampling they also **oops**, at ~0.2%, and the traces are more specific than the 2-vCPU ones. Same cell (HQ Vera, stock Firecracker v1.16.1, guest `6.12.34`, daemon `rlp-rs-0.4.1`), `vcpus=1` on every sandbox, image `dtgraviet/vera-agent-benchmark:v3` whose entrypoint starts `python -m workload.agent` immediately on resume.

### The traces

All three crashed at guest uptime **1.16–1.18 s**, and this template's snapshot instant is ~1.15 s — i.e. **10–30 ms after resume** — in the entrypoint process or its `bash` parent.

Two were identical:

### Rates

| population | clones | oopsed guests | client-visible failures |
|---|---|---|---|
| 5 freshly built templates × ~300 clones each | 1,497 | **3 (0.20%)** — 0, 1, 2, 0, 0 per build | 7 (0.47%) |
| one older template (built ~2 h earlier) | 2,000 | **0** | 4 (`exitCode -1`, empty output) |
| dense ladder, 8 execs per sandbox, 1 run | 176 | 2 | 8 episodes wedged |
| dense ladder, same level, later run | 176 | 0 | 0 |

So the client-visible failure rate (~0.2–0.5%) splits into oopsed guests and the earlier "daemon answers, exec never finishes / returns `exitCode -1`" class.

**Per-template variance is suggestive but not established.** 0 of 2,000 on one template against 3 of 1,497 across five fresh builds is the shape the snapshot-timing hypothesis predicts (a bad snapshot instant poisons every clone of that build), and 0/2,000 is unlikely if the rate were a uniform 0.2% (p ≈ 0.02). But 300 clones per build is too few to separate it from Poisson noise — 0,1,2,0,0 is also consistent with a constant rate. A proper version needs ~2,000 clones per build over ~10 builds.

### Why this supports the hypothesis in my earlier comment

Every victim is a process **created at or just after the snapshot/resume boundary**: the daemon forks the entrypoint when the gate is released, which is exactly when the runner resumes the clone. The corruption shows up in that process's mm within tens of milliseconds, as poisoned list entries and garbage pointers — the same class as the 2-vCPU `__rb_erase_color` / `vma_interval_tree_remove` oops, which was also an mm-metadata walk. The difference is that with 2 vCPUs it is 20–55% and with 1 vCPU it is ~0.2%.

The "settle before pausing the template" experiment I proposed earlier is still the first thing to try, and it is now testable on 1-vCPU guests too, where a 1,500-clone run gives a usable signal.

### Knock-on for anyone benchmarking

A wedged guest of this family hangs the Python SDK forever (it reads with `read=None`), so one sandbox stalls a whole run: a 176-level ladder sat 20 minutes with 1,401 of 1,408 episodes done and 7 in flight, and the rung it reported read 1.47 jobs/s against 15.2 jobs/s on the same build minutes later. Worth a client-side read timeout in any harness.
