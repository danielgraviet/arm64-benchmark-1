## Patched and measured: removing the fsync is enough (−17% burst, and it unblocks the next bottleneck)

I patched this on the HQ Vera bench cell and A/B'd it against the same binary with the fix off. The runner gained `RLP_INITDISK_MODE`:

- `copy` (default) — today's `copyFileContents`: `io.Copy` + `out.Sync()`.
- `nofsync` — `io.Copy`, no fsync.
- `sparse` — no data at all: `os.Truncate` to the master's size.

1,000 creates of an idle image (`alpine:3.20`) from 16 client processes, interleaved with controls, all on the same build (control = the patched binary with the flag unset, which reproduces the pre-patch baseline):

| | control | `nofsync` | `sparse` |
|---|---|---|---|
| step 9b (scratch + init-disk copy), p50 / p90 ms | **300 / 700** | **9 / 20** | **5 / 15** |
| POST → `running`, p50 / p90 ms | 1927 / 3035 | 1600 / 2709 | 1195 / 2337 |
| client-visible failures | 0 | 5¹ | 0 |

¹ 3 client read timeouts, 1 connection reset, 1 exec returning `exitCode -1` (the #3229 class). Not obviously attributable to the change; the sparse arm and the later combined arms (2,000 sandboxes) had none.

**The conservative fix captures essentially all of it.** Dropping the fsync takes the step from 300 ms to 9 ms; not writing the data at all saves a further 4 ms. The `sparse` variant depends on the guest never reading `vda` after resume (what the comment at `template.go:1401-1409` asserts); `nofsync` does not depend on that, so it looks like the better trade.

Combined with the cgroup-pool fix (#3261), the ARP fix (#3265) and the accept backlog (#3269), the same burst goes to **p50 1054 ms / p90 1748 ms** (2 runs, 2,000 sandboxes), against a control range of 1743–2294 ms p50 across 4 runs.

Patch (measurement build, flag defaults to today's behaviour):

```go
// provisionInitdisk creates the clone's PRIVATE vda target. Mode is RLP_INITDISK_MODE.
func provisionInitdisk(src, dst string) error {
	switch getenv("RLP_INITDISK_MODE", "copy") {
	case "nofsync":
		return copyFileContentsNoSync(src, dst)
	case "sparse":
		fi, err := os.Stat(src)
		...
		return f.Truncate(fi.Size())  // + create/close
	default:
		return copyFileContents(src, dst)
	}
}
```

Worth noting for whoever takes this: once 9b is gone the burst is bound by the next serial step (cgroup creation, #3261), so the two fixes are worth landing together — each alone moves ~15-20%, together with the others ~45%.
