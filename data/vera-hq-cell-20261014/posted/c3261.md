## Patched and measured: a pre-created pool takes the step from 201 ms to 24 ms — but it must be warm before the burst

I implemented the "pre-create cgroups in a warm pool" option on the HQ Vera bench cell and A/B'd it against the same binary with the pool off (`RLP_CGROUP_POOL=<size>`, 0 = today's inline `mkdir`). Pool entries are single-use: a clone takes one, teardown `rmdir`s it as before, and background fillers top the pool up.

1,000 creates of an idle image, 16 client processes, interleaved with controls:

| | control | `RLP_CGROUP_POOL=1400` |
|---|---|---|
| step 9f (cgroup mkdir + register + trigger), p50 / p90 ms | **201 / 381** | **24 / 58** |
| POST → `running`, p50 / p90 ms | 1927 / 3035 | 1725 / 2653 |

**The pool has to be filled before the burst, not on first use.** My first version started the fillers lazily from the first `setupCgroup`. That is useless under exactly the load it is meant for: the kernel creates ~1160 cgroups/s in one parent, a 1k burst consumes 1000 in ~2 s, so the pool stays empty and every clone falls back to the inline mkdir. Measured that way, 9f stayed at p50 454 ms. Starting the fillers from `NewManager` (same lifetime as the netns pool, warm before the first job) is what produces the 24 ms above; in the combined arms with a pre-filled pool it was p50 139 ms (there the clones arrive much faster, so the pool is partly drained mid-burst — a bigger pool or more fillers would close that).

Two things a real implementation has to deal with, which the measurement build does not:

1. **Adoption.** A pool entry's name cannot encode the VM id, so `cgroupDirFor(vmID)` (used by `adopt.go` at startup) can no longer find a VM's cgroup after a runner restart, and usage falls back to `/proc`. Either persist the mapping or name entries by slot and record the slot on the VM.
2. **Reuse vs single-use.** I kept single-use (teardown still `rmdir`s), so the kernel still pays for 1,000 creates per 1k burst — just off the critical path. Returning emptied cgroups to the pool would avoid the create entirely, at the cost of making sure no charge from the previous tenant survives.

For reference, the cost is dominated by the `memory` controller, which `deploy/rlp-cgroup-setup` enables under `rlp.slice/vms` and which is needed there (usage, admission floors, balloon). 1,000 `mkdir`s, 256-way parallel, on this 352-CPU host:

| controllers | parallel | serial |
|---|---|---|
| `cpu memory pids` (production) | 0.86 s | 1.21 s |
| `cpu memory` | 0.88 s | 1.20 s |
| `cpu` only | 0.47 s | 0.92 s |

Combined with #3260, #3265 and #3269 the burst goes from p50 1927 ms to **1054 ms**.
