## Patched and measured: a permanent neighbour entry on the inner tap removes the stall entirely

Implemented option 1 from the issue on the HQ Vera bench cell: `pinGuestNeigh()` next to the existing `pinTapMAC()` in both tap-setup paths (`setupInnerTap` and `replaceInnerTap`), installing `NUD_PERMANENT` for `innerGuestIP → macFromIP(innerGuestIP)` on `rlptap0`. Both values are compile-time constants of the frozen inner identity, so one entry per slot is valid for every tenant the slot will ever hold — the same argument that lets `pinTapMAC` fix the MAC in the other direction. Gated `RLP_NEIGH_PERMANENT=1` for the A/B.

60 sequential creates of an idle image on an otherwise idle host, same binary, flag off vs on:

| | control | `RLP_NEIGH_PERMANENT=1` |
|---|---|---|
| clones stalled (`toolbox_wait_ms` > 100) | **4 / 60 (7%)** | **0 / 60** |
| max `toolbox_wait_ms` | **580 ms** | **2 ms** |
| POST → `running` p50 / p90 / p99 | 67 / 75 / **658** ms | 66 / 73 / **81** ms |

With every fix on (this plus #3260/#3261/#3269): p50 **64 ms**, p90 69 ms, max **73 ms** — the tail is gone, not just shortened.

(The stall rate varies with how the probe races the restore: 23–27% in the earlier 200- and 60-create runs, 7% in this one. It is 0 with the entry installed in all of them.)

Two notes for whoever picks this up:

- This fixes the symptom at the runner. The daemon's resume detector is still broken on arm64 (`garp.rs` keys on a monotonic-clock jump that a restored guest does not have — see the #767 comment), so any resume path that does not go through a pool netns still relies on the 1 s keepalive. Worth fixing on its own.
- The entry dies with the netns, so there is nothing to clean up; `replaceInnerTap` reinstalls it when a slot's tap is recycled.
