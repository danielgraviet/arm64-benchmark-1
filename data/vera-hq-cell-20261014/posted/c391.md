## Measured evidence: NUMA locality halves 1k-burst startup on HQ Vera

Adding measurements from a benchmark cell on the HQ Vera host (2 × 88 cores, SMT2, node0 = CPUs 0-87,176-263). This issue is still unimplemented, and the data says it is the largest startup lever on this host.

**Setup.** daytona `f0611fa13` + EROFS 4 KiB blocks (#1060) + the `RLP_FC_SOCK_WAIT_MS` knob from #3212 (set to 30000, so no spawn timeouts or self-cordons in any arm). Daemon `rlp-rs-0.4.1`, stock Firecracker v1.16.1, host kernel `6.17.0-1032-nvidia-64k`, `preempt=none`. Workload: 1,000 concurrent creates from a snapshot, 1 vCPU / 64 MiB / 1 GiB disk, ready = `echo ready` answered through the toolbox. One runner, `RLP_VM_CONCURRENCY=512`.

**Arms.** Pinning was applied from outside the runner with cgroup cpusets (`rlp.slice` and `rlp.slice/vms`: `cpuset.cpus=0-87,176-263`, `cpuset.mems=0`). The API stayed unpinned in both arms. Arms were interleaved (unpinned, pinned, unpinned), 3 reps each.

(The three single failures in the unpinned arms are the post-resume guest hang tracked in #3213, not placement.)

**Observations**

- Pinning runner + sandboxes to one node cuts the 1k all-ready time from **20–28 s to 8–9 s** and p95 by **~2.4×**.
- The second socket buys nothing for this burst. A separate run put the control plane (API, Postgres, NATS, proxy) on node 1 and runner + sandboxes on node 0; all-ready was the same as with everything on node 0.
- Things that were ruled out as the cause on the same host: toolbox proxy capacity (1 proxy vs LB→1 vs LB→4, identical), event auditing, API restart / row accumulation, the SMT Firecracker fork for 1-vCPU guests.
- The published HQ Vera "10.8 s for 1,000 sandboxes" figure was taken with `rlp.slice` pinned to socket 0, so it is a one-node configuration. An unpinned runner on the same host reproduces ~20–23 s.

**Implication for the design.** For burst startup, the cheapest form of this issue may be **one runner per NUMA node** (each runner's slice bound to its node's CPUs and memory, registered as separate runners), rather than per-VM node selection inside one runner. That keeps every sandbox's vCPU threads, guest memory, tap/netns work and the runner's own threads on one node, and doubles the per-host runner parallelism without cross-node traffic. Per-VM placement inside one runner would still need the runner's own hot paths (spawn, netns, snapshot load) to be node-local to get the same effect.
